# T2 · OpenLibrary-Suche für den Katalog

---

## Kontext

Das Projekt ruft OpenLibrary bereits auf – aber ausschließlich intern für den Beschaffungsfluss im `procurement`-Kontext. Der vorhandene `OpenLibraryClientAdapter` (`procurement/adapters/out/external/`) hat dabei drei Einschränkungen, die ihn für eine Katalogsuche unbrauchbar machen:

1. **Suchanfrage ist ISBN-only.** Der Aufruf lautet `?isbn={isbn}&limit=1&fields=title,isbn,key`. Nutzer sollen aber nach Titel oder Autor suchen können.
2. **Rückgabe ist auf 1 Ergebnis begrenzt.** Eine Suchmaske braucht eine Liste von Treffern (z. B. 10).
3. **Fehlende Felder.** Autor (`author_name`) und Cover-ID (`cover_i`) werden nicht angefragt, sind aber für die Trefferanzeige und Detailansicht notwendig.

Hinzu kommen kleinere technische Schulden in der bestehenden Datei: falsches Log-Label (`"Payment-Service"` statt `"OpenLibrary"`), `System.out.println`-Aufrufe und ein `Thread.sleep(3000)` in `orderBook()`.

### Ziel

Einen neuen Output-Port `LibrarySearchClient` im `catalog`-Kontext definieren und einen dedizierten Adapter `OpenLibraryCatalogAdapter` implementieren, der für freie Texteingaben eine Liste von Suchergebnissen zurückgibt. Parallel dazu werden die technischen Schulden im bestehenden `OpenLibraryClientAdapter` bereinigt.

### Architektonische Entscheidung: Neuer Adapter statt Erweiterung

Der bestehende `OpenLibraryClientAdapter` gehört zum `procurement`-Kontext und implementiert den `ProcurementClient`-Port. Ihn direkt um einen `catalog`-Port zu erweitern würde eine unerwünschte Abhängigkeit zwischen zwei Bounded Contexts auf Adapterebene erzeugen.

**Lösung:** Neuer `OpenLibraryCatalogAdapter` im `catalog`-Kontext. Beide Adapter verwenden denselben `RestTemplate`-Bean aus `common/config/AppConfig.java`, ohne voneinander zu wissen.

### OpenLibrary-API

Bestehend (procurement): `GET /search.json?isbn={isbn}&limit=1&fields=title,isbn,key`

Neu (catalog): `GET /search.json?q={query}&limit=10&fields=title,author_name,isbn,cover_i,key`

Beispielantwort:
```json
{
  "docs": [
    {
      "title": "The Lean Startup",
      "author_name": ["Eric Ries"],
      "isbn": ["9780307887894"],
      "cover_i": 8091016,
      "key": "/works/OL16528660W"
    }
  ]
}
```

Cover-URL-Schema: `https://covers.openlibrary.org/b/id/{cover_i}-M.jpg`

## Aufgabe

### 1. `BookSearchResult` – Ergebnistyp

Record in `catalog/application/` als Datencontainer für einen einzelnen Suchtreffer. Alle Felder außer `title` sind nullable, da OpenLibrary-Einträge unvollständig sein können.

```java
package de.demo.lending.catalog.application;

public record BookSearchResult(
        String isbn,
        String title,
        String author,
        String coverUrl,
        String openLibraryKey
) {}
```

Keine Validierung – der Record ist ein reines Transferobjekt zwischen Adapter und Application Service.

### 2. `LibrarySearchClient` – Output Port

Interface in `catalog/application/ports/out/`. Definiert den Vertrag für externe Buchsuche aus Sicht des `catalog`-Kontexts.

```java
package de.demo.lending.catalog.application.ports.out;

import de.demo.lending.catalog.application.BookSearchResult;
import java.util.List;

public interface LibrarySearchClient {
    List<BookSearchResult> search(String query);
}
```

### 3. `OpenLibraryCatalogAdapter` – Adapter

Implementierung von `LibrarySearchClient` in `catalog/adapters/out/external/`. Nutzt den vorhandenen `RestTemplate`-Bean.

**Verhalten:**
- URL-Kodierung der Suchanfrage per `URLEncoder.encode(query, StandardCharsets.UTF_8)`
- API-Aufruf: `GET https://openlibrary.org/search.json?q={query}&limit=10&fields=title,author_name,isbn,cover_i,key`
- Response-Typ: `Map` (konsistent mit dem bestehenden Adapter)
- Mapping der `docs`-Liste auf `List<BookSearchResult>`

**Mapping-Regeln pro Treffer:**

| OpenLibrary-Feld | Typ in JSON | Zielfeld in `BookSearchResult` | Fallback |
|------------------|-------------|-------------------------------|---------|
| `title` | `String` | `title` | `"Unbekannter Titel"` |
| `author_name` | `List<String>` | `author` (erstes Element) | `null` |
| `isbn` | `List<String>` | `isbn` (erstes Element) | `null` |
| `cover_i` | `Integer` | `coverUrl` (als vollständige URL) | `null` |
| `key` | `String` | `openLibraryKey` | `null` |

Cover-URL-Aufbau: `"https://covers.openlibrary.org/b/id/" + coverId + "-M.jpg"`

**Fehlerbehandlung:**
- Bei `HttpClientErrorException` oder `HttpServerErrorException`: Logging + leere Liste zurückgeben (kein throw)
- Bei leerem oder null `docs`-Feld: leere Liste zurückgeben
- Einträge ohne `title` werden übersprungen (`.filter`), nicht abgebrochen

**Nicht implementieren:** Retry-Logik, Caching, Paginierung, Timeouts (v1-Scope).

### 4. Bereinigung im bestehenden `OpenLibraryClientAdapter`

Datei: `procurement/adapters/out/external/OpenLibraryClientAdapter.java`

Folgende Probleme beheben – **keine inhaltlichen Änderungen am Suchverhalten**:

| Problem | Zeile (ca.) | Korrektur |
|---------|-------------|-----------|
| `log.info("Synchroner REST-Call zu Payment-Service …")` | 35 | Log-Text auf `"OpenLibrary-Suche"` korrigieren |
| `log.info("Inventory-Service antwortete: …")` | 37 | Log-Text auf `"OpenLibrary antwortete: …"` korrigieren |
| `System.out.println(…)` in `determineBook()` | 99–101 | Durch `log.info` / `log.warn` ersetzen |
| `Thread.sleep(3000)` in `orderBook()` | 80 | Entfernen; Methode gibt direkt `UUID.randomUUID().toString()` zurück |

## Akzeptanzkriterien

- [ ] `BookSearchResult` ist ein Java Record im Package `de.demo.lending.catalog.application` mit den fünf Feldern `isbn`, `title`, `author`, `coverUrl`, `openLibraryKey`.
- [ ] `LibrarySearchClient` ist ein Interface im Package `de.demo.lending.catalog.application.ports.out` mit der Methode `List<BookSearchResult> search(String query)`.
- [ ] `OpenLibraryCatalogAdapter` implementiert `LibrarySearchClient`, liegt im Package `de.demo.lending.catalog.adapters.out.external` und enthält **keine** Imports aus `procurement`, `loan`, `inventory` oder `payment`.
- [ ] Der Adapter nutzt die Request-URL `https://openlibrary.org/search.json?q=…&limit=10&fields=title,author_name,isbn,cover_i,key`.
- [ ] Ein curl-Aufruf gegen den späteren Endpunkt (T3) liefert Treffer mit Titel, Autor, ISBN und Cover-URL – oder eine leere Liste bei keinem Treffer. *(Verifizierbar nach T3.)*
- [ ] Bei einer nicht erreichbaren OpenLibrary-API gibt der Adapter eine leere Liste zurück, die Anwendung wirft keine unbehandelte Exception.
- [ ] `OpenLibraryClientAdapter` enthält kein `Thread.sleep` und keine `System.out.println`-Aufrufe mehr; Log-Labels sind auf OpenLibrary korrigiert.
- [ ] `mvn compile` läuft ohne Fehler durch.
- [ ] Das bestehende Szenario „Ausleihe mit Beschaffung" funktioniert weiterhin: Der `procurement`-Kontext nutzt nach wie vor `ProcurementClient` / `OpenLibraryClientAdapter` ohne Änderung am Verhalten.
