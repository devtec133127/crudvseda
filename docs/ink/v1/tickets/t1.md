# T1 · Catalog Domain und Persistenz

---

## Kontext

Das Projekt besitzt bisher keinen Bounded Context für einen Buchkatalog. Bücher existieren im System nur als `InventoryCopy` (physisches Exemplar im `inventory`-Kontext) oder als Zwischenergebnis bei der Beschaffung (`ProcurementOrder`). Es gibt kein Domänenobjekt, das ein Buch als konzeptionellen Katalogeintrag abbildet – also unabhängig davon, ob Exemplare davon vorhanden sind oder nicht.

Ziel dieses Tickets ist es, einen neuen Bounded Context `catalog` zu schaffen, der genau diesen fehlenden Begriff einführt: `CatalogBook` – ein Buch, das ein Bibliothekar bewusst in den eigenen Katalog aufgenommen hat. Dieser Kontext bildet das Fundament für alle weiteren Tickets des Produktinkrements v1 (Suche, Verwaltungs-API, Frontend).

Der neue Context folgt exakt dem bestehenden Hexagonal-Muster des Projekts:

```
Domain → Application Ports → Adapter (Persistence)
```

Kein Event, kein Kafka, keine Verbindung zu `loan`, `inventory` oder `payment`. Der `catalog`-Kontext ist in v1 vollständig synchron und REST-getrieben.

### Einordnung in die Gesamtarchitektur

```
de.demo.lending/
├── loan/           ← unverändert
├── inventory/      ← unverändert
├── procurement/    ← unverändert
├── payment/        ← unverändert
└── catalog/        ← NEU (dieses Ticket)
    ├── domain/
    ├── application/
    └── adapters/
```

### Referenzimplementierung

Als Orientierung dienen:
- `inventory/domain/InventoryCopy.java` – Domänenobjekt ohne AggregateRoot
- `inventory/adapters/out/persistence/InventoryCopyEntity.java` – JPA Entity mit Lombok-Builder
- `inventory/adapters/out/persistence/InventoryRepositoryAdapter.java` – Port-Adapter-Muster
- `inventory/adapters/out/persistence/SpringInventoryCopyRepository.java` – Spring Data JPA Interface
- `common/valueobjects/Isbn.java` – vorhandenes Value Object (nicht nochmals anlegen)

## Aufgabe

### 1. Package-Struktur anlegen

```
src/main/java/de/demo/lending/catalog/
├── domain/
│   ├── CatalogBook.java
│   └── CatalogBookId.java
├── application/
│   └── ports/
│       └── out/
│           └── CatalogBookRepository.java
└── adapters/
    └── out/
        └── persistence/
            ├── CatalogBookEntity.java
            ├── SpringCatalogBookRepository.java
            └── CatalogBookRepositoryAdapter.java
```

### 2. `CatalogBookId` – Value Object

UUID-basiertes Value Object nach dem Muster der vorhandenen IDs (z. B. `LoanId`, `CopyId`).

```java
package de.demo.lending.catalog.domain;

import java.util.UUID;

public record CatalogBookId(UUID value) {
    public static CatalogBookId newId() { return new CatalogBookId(UUID.randomUUID()); }
    public static CatalogBookId of(UUID value) { return new CatalogBookId(value); }
}
```

### 3. `CatalogBook` – Domänenobjekt

Kein `AggregateRoot` (keine Domain Events in v1). Einfache Klasse mit privaten Feldern und Factory-Methode.

Felder:

| Feld | Typ | Pflicht | Bemerkung |
|------|-----|---------|-----------|
| `id` | `CatalogBookId` | ja | UUID, intern vergeben |
| `isbn` | `String` | nein | Nicht alle OpenLibrary-Einträge haben ISBN; kein `Isbn`-VO verwenden, da externe Daten nicht immer valide sind |
| `title` | `String` | ja | Buchtitel |
| `author` | `String` | nein | Erster Autor aus OpenLibrary |
| `coverUrl` | `String` | nein | z. B. `https://covers.openlibrary.org/b/id/12345-M.jpg` |
| `openLibraryKey` | `String` | nein | OpenLibrary-Werk-Schlüssel, z. B. `/works/OL1234W` |
| `addedAt` | `Instant` | ja | Zeitpunkt der Aufnahme in den Katalog |

Factory-Methode `CatalogBook.add(...)` setzt `id` und `addedAt` automatisch.

### 4. `CatalogBookRepository` – Output Port

```java
package de.demo.lending.catalog.application.ports.out;

import de.demo.lending.catalog.domain.CatalogBook;
import de.demo.lending.catalog.domain.CatalogBookId;
import java.util.List;
import java.util.Optional;

public interface CatalogBookRepository {
    void save(CatalogBook book);
    Optional<CatalogBook> findById(CatalogBookId id);
    List<CatalogBook> findAll();
    void deleteById(CatalogBookId id);
}
```

### 5. `CatalogBookEntity` – JPA Entity

Tabelle `catalog_book`. Lombok-Annotationen wie in allen anderen Entities: `@Getter`, `@Setter`, `@NoArgsConstructor`, `@AllArgsConstructor`, `@Builder`.

| Spalte | Typ (JPA) | Pflicht |
|--------|-----------|---------|
| `id` | `UUID` (`@Id`) | ja |
| `isbn` | `String` | nein (`nullable = true`) |
| `title` | `String` | ja (`nullable = false`) |
| `author` | `String` | nein |
| `coverUrl` | `String` | nein |
| `openLibraryKey` | `String` | nein |
| `addedAt` | `Instant` | ja |

### 6. `SpringCatalogBookRepository` – Spring Data Interface

```java
public interface SpringCatalogBookRepository extends JpaRepository<CatalogBookEntity, UUID> { }
```

Keine Custom Queries nötig – `findAll()`, `findById()`, `save()`, `deleteById()` kommen aus `JpaRepository`.

### 7. `CatalogBookRepositoryAdapter` – Adapter

Implementiert `CatalogBookRepository`. Enthält die Mapping-Logik `domain ↔ entity` als private Methoden `toDomain(entity)` und `toEntity(domain)`.

## Akzeptanzkriterien

- [ ] Das Package `de.demo.lending.catalog` existiert mit den Unterpackages `domain`, `application.ports.out` und `adapters.out.persistence`.
- [ ] `CatalogBookId` ist ein Java Record mit `newId()` und `of(UUID)` Factory-Methoden.
- [ ] `CatalogBook` hat alle sieben Felder (id, isbn, title, author, coverUrl, openLibraryKey, addedAt) und eine statische `add(...)`-Factory-Methode, die `id` und `addedAt` intern setzt.
- [ ] `CatalogBookRepository` definiert die vier Methoden: `save`, `findById`, `findAll`, `deleteById`.
- [ ] `CatalogBookEntity` ist mit `@Entity` und `@Table(name = "catalog_book")` annotiert; alle Felder sind korrekt gemappt.
- [ ] `SpringCatalogBookRepository` erweitert `JpaRepository<CatalogBookEntity, UUID>`.
- [ ] `CatalogBookRepositoryAdapter` implementiert `CatalogBookRepository` vollständig; das Mapping zwischen Domain und Entity funktioniert in beide Richtungen.
- [ ] Die Tabelle `catalog_book` wird beim Anwendungsstart durch Hibernate DDL automatisch erstellt (konsistent mit dem bestehenden `spring.jpa.hibernate.ddl-auto: create`-Setting).
- [ ] Die Anwendung startet ohne Fehler (`mvn spring-boot:run` nach `docker-compose up -d`).
- [ ] Es gibt keine Import-Abhängigkeit von `catalog` in Richtung `loan`, `inventory`, `procurement` oder `payment` (der neue Kontext ist isoliert).
